# قائمة الإطلاق — حلقاتي (من 2.65 إلى 3.0.0)

لا تُسمّى نسخة «3.0.0» إلا عند تحقق كل البنود. حتى ذلك الحين تبقى الإصدارات RC.

## قبل أي نسخة تصل للمستخدمين
1. البناء في GitHub ناجح (اختبارات، lint، توقيع) وبصمة الـ APK مطابقة للمنشورة.
2. فحوصات المصدر (`rc29`, `rc30` وما قبلها) تنجح.
3. تثبيت النسخة فوق النسخة السابقة على جهازين مختلفين بلا فقد بيانات.
4. تجربة كل دور بحساب حقيقي: مدير، مشرف، محفّظ، ولي أمر (ما يراه وما لا يراه).
5. للإصدارات التي تغيّر الأرقام (مقرر، جودة، إشعارات): مقارنة 5 طلاب على الأقل بين الشاشة والإشعار والتقرير.

## قاعدة البيانات
- قبل أي ملف SQL: نسخة احتياطية (Supabase → Database → Backups)، ثم تطبيق الملف مرة واحدة بالترتيب.
- لا يُطبَّق SQL على الإنتاج قبل تجربته في معاملة تُلغى (ROLLBACK) أو على نسخة تجريبية.
- في Supabase → Authentication → Password security: فعّل «Leaked password protection».

## النشر
- شغّل workflow الإصدار بـ `variant = release`. خيار `mandatory`: اتركه `false` إلا إذا كان الإصدار يصحح بيانات خاطئة أو ثغرة.
- التحديث الإلزامي يمنع **كل** النسخ القديمة من الفتح حتى تُحدَّث، ولا يمكن الرجوع لنسخة أقدم (رقم الإصدار لا ينقص). لذلك الإصلاح الخاطئ يعني إصدارًا جديدًا.
- لنشر التحديث على الويب: ارفع `Halaqati-vX-publish-update.zip` إلى جذر مستودع `halaqati-web` (يقرؤه workflow الصفحات كل ساعة أو عند الدفع).

## الحلقة التجريبية (قبل الجميع)
- 3 إلى 5 محفّظين فعليين يستخدمون النسخة أسبوعًا. يُبلَّغون بزر «إرسال تقرير مشكلة» في الإعدادات.
- لا يُنشر الإصدار للجميع قبل أسبوع بلا عيب حرج.

## شروط تسمية 3.0.0
- بناء كامل ناجح، تجربة ترقية بجهازين، أدوار أربعة، أسبوع تجريبي، نسخة احتياطية للقاعدة، وترحيلات مطبّقة بترتيب موثّق.
